> | 10-11 | Workspace ownership, basic RBAC | Plane: workspace members; Owner can invite, member can view | Member rows, role checks |

Day 8-9 put a **badge reader** at the **front of the house**: the door now answers *who you are* (`request.user.sub`) before any room. Day 10-11 climbs **one layer up** and asks the question the badge *cannot* answer: *are you **allowed* in **this** workspace?* That is the **authorizer** — a membership table in the **cellar** + a role check per room. The restaurant analogy: the badge gets you past the **front door**; membership is the **key to *your* private dining room** — the door tells us *your name*, the key tells us *which rooms are yours*.

## Today's Deliverables (the ask)

### A. Code-side changes (both tracks, in parallel — the *authorizer* layer)

1. **A membership table, both tracks** (this is the *one* new schema surface the day owns — everything else is read-model):
   - `workspace_members` — `id` (uuid, PK, same `ids.ts`/`ids.py` generator as the sibling tables), `workspace_id` (FK → `workspaces.id`, `ON DELETE CASCADE` — a deleted workspace takes its keys with it; *this is the existing cascade the ADR-007 error contract already models, now with a third table in the chain*), `user_id` (the badge's `sub` — *never* a free-form string; it is *the* Auth0 principal, and both kitchens use the field `user_id` to map Auth0's `sub` onto a stable column name), `role` (`owner` | `member`; a **CHECK** constraint, not an enum type, both tracks — the *minimum* the roadmap calls for), `created_at` (`now()` default, matching its siblings), plus a **unique index on `(workspace_id, user_id)`** (a user is a member of a workspace *at most once*) and an **index on `user_id`** (the "all workspaces I belong to" query in A.3). *The role is a row, not a claim* — see Decide-1 for why it *cannot* live in the badge.
   - The two tracks' **migration story** (ADR-005) *grows* this table in both kitchens: TS → the Drizzle table in `ts/src/db.ts` + a **new migration** in the Drizzle migration dir; PY → the `WorkspaceMemberModel` in `py/src/models.py` + a **new alembic revision**. *Name the revision/migration file* in the breakdown. The cellar (ADR-008, ADR-010) is still **doorless** — the migration *applies* but CI runs *cellar-less*, so the table's *presence* is not a CI dependency; only the *code path* that reads it is (and that path is stubbed, per B).
2. **The authorizer function, both tracks** — *pure*, one file each mirroring the reader's *reader/seam* discipline from ADR-011 (a pure `authorizeRole(…)` that *does not know about HTTP*, called by a thin hook/middleware):
   - **TS** in `ts/src/` (the breakdown picks a name — `authorize.ts` is the honest default; a `middleware/` directory is a *make-it-right* move *not* done today, say so): **`assertRole(request, workspaceId, minRole)`** → resolves the *resource's workspace* (`workspaceId`, or — for project/issue routes — *walks up* `project.workspace_id` / `issue.project_id → project.workspace_id`), reads **`request.user?.sub`**, looks up **`workspace_members`** for that `(workspaceId, sub)`, and either *continues* or **throws `ForbiddenError`** (a *new* ADR-007 resident, see A.4). The *role ladder* is explicit: `owner > member` — a *check* like `rank(role) >= rank(minRole)`, not string equality, so "owner" satisfies an "owner-or-above" check and "member" does *not*.
   - **PY** in `py/src/` (mirror: `authorize.py`): **`assert_role(request, workspace_id, min_role)`** reading **`request.state.user["sub"]`**, same lookup, same ladder, same throw. The *two* kitchens reach the *same* decision from the *same* two inputs (workspace, sub); only the ORM differs (SQLAlchemy vs Drizzle). **Parity bar (ADR-001): the same request, the same membership state → the same outcome on 8000 and 8001** — a third gate to the parity wall, *after* ADR-007 (status/envelope) and ADR-011 (the six 401 strings).
3. **Which routes gate, at what level** — the breakdown *explicitly* names each data route and its `minRole` (roadmap: **Owner can invite, member can view**):
   | Route | minRole | why |
   |---|---|---|
   | `GET /workspaces` (*mine*) | `member` (or: no role — *sees only workspaces I belong to*, the `user_id = sub` filter **replaces** "see all") | a *member* sees their own rooms; a stranger sees none — the **list route's security is membership, not a badge** |
   | `POST /workspaces` | `member` (or: *any authenticated user*) — **creator becomes `owner`** | making a room: the maker is its owner (one row, `role=owner`), *this is how the first key is minted* |
   | `GET/PUT/DELETE /workspaces/:id` (`:id` is the workspace) | `owner` | *own* your room's key — **delete = owner only** (roadmap's "owner … invites", a member does *not* delete) |
   | `GET/POST /workspaces/:id/projects` · `/workspaces/:id/projects/:projectId` | `member` (view/create) · project *delete* → `owner` | a member works in the room; only the owner pulls the room's keys out |
   | `GET/POST /workspaces/:id/projects/:projectId/issues` · `…/issues/:issueId` | `member` (view/create) · issue *delete* → `owner` | same ladder, one room deeper |
   | **new:** `POST /workspaces/:id/members` (**invite**) | `owner` | *the* roadmap move — an **owner** mints a `member`/`owner` key for another `user_id` (their Auth0 `sub`); a member **cannot** invite |
   | **new:** `GET /workspaces/:id/members` | `member` | a member can *see the room's key-ring*; only an owner writes to it |
   - **Projects and issues inherit the workspace gate** — they do **not** get their *own* membership rows (that is *later*, a *different* day); their workspace is resolved by *walking up* the FK chain *inside* `assertRole`. *One* membership table, *three* levels of room depth, *no* per-project keys — the *thin* house.
4. **403 into the ADR-007 contract, both tracks** — the authorizer introduces **`ForbiddenError`** → `{ statusCode: 403, error: "Forbidden", message }`. **401 vs 403 is the *entire* conceptual split of the day and must be stated in one line each:** *401 = we do not **know** who you are* (the door/reader, ADR-011) vs *403 = we **know** you but you are **not allowed*** (the authorizer, this day). The **401 is *first*** — a no-badge request 401s at the door and *never reaches* the authorizer; the 403 is *only* for a *badged* caller who lacks the *role*. The *message* strings must be *typed* (a **two-or-three-string** contract mirroring ADR-011's six-string discipline): `Not a member of this workspace` / `Requires the owner role` (the breakdown names the exact set; *both kitchens, same strings*). **This is a *new resident* of the receptionist** — the ADR-007 envelope *shape* is unchanged (`error` is now `"Forbidden"`); a **403 contract test** in the CI suite is the payoff (B).
5. **The *invite* happy-path's one honest limit** — `POST …/members` *creates a `pending` role row* **if** the day adopts Plane's `membership_state`; **but it does *not* email** (an email/notification provider is a *later* day, ADR-007's "no-improvisation" means we *do not* silently fake a confirmation). State exactly what "invite" *does* today (a row in the cellar, *returned* in the response) vs what it *does not* (no outbound mail, no badge minting — the *invited* person already has an Auth0 badge; the owner just *grants* them a room key). If the day opts to skip `membership_state` and ship *only* `role` (simpler, still meets "owner invites, member views"), *say so and record it* — that is a legitimate thin-house cut, but it is a **named** cut, not an accident.

### B. Test-side (the ADR-010 doorless, cellar-less gate is *load-bearing* here — this is the day's hardest design question)

*The core tension:* the authorizer *reads a role from the cellar* (`workspace_members`) — but **ADR-010's CI is *cellar-less*** (no Postgres in the gate) **and doorless** (`AUTH0_DOMAIN` unset → `request.user` is *undefined*, the ADR-011 doorless path). A *membership lookup* that hits a *dead cellar* in CI would 500. So the authorizer's tests must be **constructible without either the cellar or a live badge.** Resolve this *before* writing tests (Decide-1) and keep the ADR-010 gate green:

1. **The doorless authorizer decision (Decide-1, the day's one ADR-grade choice):** when **`request.user` is undefined** (no badge — the *exact* state CI runs), what does `assertRole` do? The options, *pick one, record the ADR consequence in a sentence*:
   - **(a) Fails closed** → the *whole* data surface is **403 (or 401) under doorless** — the *honest* security posture (a role a stranger *cannot* hold means a stranger *cannot* read a workspace), **but** it **breaks the *existing* ADR-007 500/404 tests** that hit data routes *doorless* and expect the *dead-cellar 500* (the ADR-010 welded test) — those tests would now *403 first*. **(b) Passes through (open)** → doorless keeps *today's* route behavior *exactly* (a no-badge caller behaves as it does now; the *role* check is a *no-op* when there is *no* `sub`) — the **CI 500/404 tests survive untouched**, the *local* dev story is unchanged, **but** "open under doorless" is a **named, deliberate** posture the ADR must *state* (it is ADR-011's *doorless = "no `AUTH0_DOMAIN`"* applied *a layer up*: no badge ⇒ the *authorizer* is absent, just as no badge ⇒ the *reader* is absent). **Recommendation: (b)**, *mirroring ADR-011's doorless shape at the authorizer* — the reader *and* the authorizer both *vanish together* under doorless, so the **one** "no `AUTH0_DOMAIN`" key gates *both* layers coherently, and the *entire* existing suite (ADR-007 500/404, ADR-011 lighthouse, the 6-string 401) is *untouched*. **State the *negative* of the chosen posture in the ADR** (e.g. under (b): "a caller *without* a badge reaches the *same routes* they did pre-Day-8; RBAC is *only* enforced once the door is *configured* — CI cannot exercise RBAC *with* a badge and *without* a cellar, so RBAC is *locally* tested, not *in* CI"). The *only* *permitted* asymmetry across the two kitchens is one that is *named*.
2. **How RBAC is *actually* exercised if not in CI, then** (under (b)): the **authorizer's *negative* logic is *pure*** — `assertRole` takes `(workspaceId, sub, minRole)` + a *membership input* and returns *allow/throw*, with **no HTTP, no cellar** in the *pure* function. So the *real* coverage is a **unit suite** in each kitchen that **stubs the one membership read** (the breakdown names the seam: a `findMembership(workspaceId, userId)` dependency the *hook* injects, *swapped for a fake* in tests) and feeds it *membership states* — (i) no row → 403 `Not a member`, (ii) row `member` + `minRole=owner` → 403 `Requires the owner role`, (iii) row `owner` + `minRole=owner` → pass, (iv) row `member` + `minRole=member` → pass. **These pass *cellar-less and doorless* in CI** (the *pure* function, a faked membership read — *no* JWKS, *no* Postgres, *no* live badge). The *one* thing *not* in CI is the *integration* of the *real* membership row → *real* request under a *real* configured door — the *same* class of **named debt** as ADR-011's *live-JWKS* (the *configured-door happy path* is **local / day-9-live*, not the zero-service gate). Keep **both** kitchens' *pure* authorizer suites *symmetric* (a third parity-surface test pair, like the 6-string pair).
3. **The *existing* suite is *sorted* against the authorizer, honestly** (the day-08 "sort the suite against the door" move, *again*):
   - The **6-string 401 tests** (ADR-011) hit routes **doorless** (*no* badge) → the *door is absent* → they **survive untouched** (they never reach the authorizer).
   - The **lighthouse/menu tests** (ADR-010/ADR-011) hit `PUBLIC_PATHS` → the door **returns early** before the authorizer → **survive untouched**.
   - The **ADR-007 500/404** tests: *survive iff Decide-1 = (b)** (doorless authorizer passes through). Under (a) they must be *re-aimed* — *this is the whole cost of (a)*; state it.
   - The **new authorizer unit tests** (item 2) are the *addition*.
   - **`uv run pytest -q` and `pnpm test` must pass with *zero services*** — the conftest `:9` trick *unchanged*; the authorizer stands *behind* the door and *in front of* the dead cellar, and under doorless it is *absent*.
