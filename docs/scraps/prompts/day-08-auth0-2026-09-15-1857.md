## The Doorless/CI Question (settle this first — it decides the tests)

Day 8 introduces an **external service** (Auth0) into an app whose CI is a locked **zero-service boundary** (ADR-010: unroutable `127.0.0.1:9`, in-process, 0 skipped). The breakdown must pick the test-token mechanism and must preserve ADR-010:

1. **Local-sign, production-verifies** — the app accepts a *key configuration* (HS256 secret **or** Auth0 JWKS URL) per env; **test = local HS256 key** signing a synthetic `sub` token, **prod = Auth0 domain + JWKS**. The same verification function, two configurations. CI stays zero-service because the *test* config needs no network. This is the ADR-008-shaped answer (config door, no code split) and the recommended pick.
2. **Test bypass** — a `TEST_MODE` flag that skips verification and injects a canned user. Cheap but it **splits the code path** — the very sin ADR-008 committed on the compose side. If chosen, the breakdown must say why a config-door can't cover it.
3. **Call real Auth0 in CI** — a free-tier Auth0 app in the runner. Violates ADR-010's zero-service boundary and spends the free tier on CI; the breakdown would have to justify breaking a *locked* decision 3 days old, and it would also make CI flaky (network). Recommend **against**.

**Requirement**: pick one and state the **dual-track consequence in one line** (per ADR-001): v1 = `python-jose`/`pyjwt`, v2 = `fast-jwt` (or `@fastify/jwt`) — same *concept* (verify a bearer token, map failures to the ADR-007 pattern), different libraries, and the **same** count of auth tests on both sides where the mechanism allows. Never silently let one track verify what the other fakes.

**Second sharp decision (same question family, different axis)**: v1 (Starlette closures) has **no dependency-injection seam** for auth — the day-7 v2 note already flagged the route shape. The breakdown must state **exactly** how v1 attaches verification (a middleware that inspects `request.headers.authorization` and rejects with the ADR-007 `AuthError` before the route, vs. per-route inline checks, vs. an `on_startup`-wired app.state key the routes close over) and **why** — and note the v2 Fastify side has the same question with a different answer (a `fastify-plugin`-wrapped `onRequest` hook vs. `@fastify/jwt`). The mechanism must be *parallel in concept*, per ADR-004-001.
