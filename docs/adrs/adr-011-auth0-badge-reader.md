# ADR-011: Auth0 — the Badge Reader at the Counter (the door the house didn't have)

**Status**: Active
**Date**: 2026-09-21
**Phase**: Phase 1 — Make It Work, Sprint 2, Days 8-9
**Supersedes**: None (builds on ADR-008 *doorless cellar*; consumes the ADR-007 receptionist contract and the ADR-001 parity wall)
**Twin to**: ADR-008 (doorless *deploy*) — this is the doorless *reader*

## Context

By Day 7 the house had two *receptionists* (the counter's error handlers, ADR-007) that *improvised on*: the cellar (ADR-005), the menu (zod/Pydantic), and the ids. Day 7's preview promised a *third* kind the house had never carried:

> *The street may read an empty menu, but data routes need to know **who's asking**.*

A restaurant the public walks into has no *door* — every counter is on the street, and the kitchen is open. Add real sign-up and two people walk in together, and suddenly "who's asking" is the question the whole house answers *before* it answers anything else. The decision this day forced: **what does the door read, and where does it live?**

Three forces set the shape.

1. **The house already chose hosted.** The v4 roadmap names the reference *Campaign API* and its **Gatekeeper RBAC** (Auth0 hosted login). We are building the thin house, not a login system. So the *door* reads a **badge** Auth0 already minted — we never hold a password, never run a token endpoint, never *issue* the badge. We only *read and check* it. This retires the Day 3 *stub* door (`auth.ts` / `auth.py`, which returned a literal `{ sub: "dev" }`) — the stub stays *only* under the no-env doorless path, never on a configured door.

2. **The door is *one*, not per-room.** The counter is *many* rooms (workspace / project / issue, CRUD on both counters). A *global* door that runs once, at the front, before any room — a Fastify `onRequest` hook / a Starlette `BaseHTTPMiddleware` — is the only shape that scales to rooms we have not built yet (the Day 10-11 ownership model). Put the lock on each *route* and the lock has to be added to every room forever.

3. **The parity wall (ADR-001) had never met this gate.** ADR-007 made the counter *look alike* on status codes and envelopes. ADR-011 is the parity wall's *second* gate: **the badge must read the same and fail the *same*** in both kitchens — but each kitchen's crypto stack produces a *different* error shape (jose v6 vs PyJWT). The day's real engineering is the mapping from two different failure worlds to *one* six-string contract, and keeping the lighthouse (health) on the *street* while the data rooms go behind the door.

## Decision

1. **The reader is a pure function + a thin door, one per kitchen.**
   - **TS** (`apps/taskflow/ts/src/auth.ts`): a **`doorHook`** registered as a Fastify **`onRequest` hook** on the app in `server.ts` (`.addHook("onRequest", doorHook)`). It reads the **`Authorization: Bearer <token>`** header, then calls a *pure* **`verifyBadge(token, tenant, audience)`**. `verifyBadge` does the *only* crypto — `jose` **v6** `jwtVerify(token, await jwksFor(tenant), { algorithms: ["RS256"], issuer, audience })` against a **per-tenant remote JWKS** (`createRemoteJWKSet`, cached in a `Map` for the process lifetime). A structural **base64url-three-segment** regex pre-check runs *before* the crypto, so garbage reads *Malformed* and never a signature failure. On failure it throws **`UnauthorizedError`** (the ADR-007 shape); the door catches it and returns the **401 envelope**.
   - **PY** (`apps/taskflow/py/src/auth.py`): an **`AuthenticateBadgeMiddleware(BaseHTTPMiddleware)`** added via **`app.add_middleware`** in `server.py`. One **`dispatch()`** choke point. It calls the *pure* **`verify_badge(token, tenant, audience)`**, which does a **hand-rolled ~40-line JWKS reader** (fetch `/.well-known/jwks.json` once, cache by `kid`, **re-fetch exactly once on an unknown kid** — key-rotation, the one live case) and builds a `cryptography` `RSAPublicNumbers` key from the JWK `n`/`e`, then `pyjwt.decode`. On failure it raises **`UnauthorizedError`**; the middleware returns the **401 envelope**.
   - **The pure verifier is the seam.** The *reader* (HTTP: header, tenant, audience, envelope) is the kitchen-specific skin; the *badge reader* (token in, payload-or-throw out) is the parity wall — same inputs, same failure semantics, only the crypto library differs.

2. **The *six-string* 401 contract — one message per failure kind, in both kitchens.** The ADR-007 envelope *shape* is unchanged (`{ statusCode, error: "Unauthorized", message }`); what Day 8/9 adds is that `message` is *typed* into the six distinct strings the roadmap enumerates:

   | String | Meaning |
   |---|---|
   | `No token provided` | no `Authorization` header, or not a `Bearer` token |
   | `Malformed token` | structurally not a JWS (not three base64url segments) |
   | `Token expired` | `exp` in the past |
   | `Wrong audience` | `aud` ≠ the audience we accept |
   | `Wrong issuer` | `iss` ≠ the tenant's issuer |
   | `Signature verification failed` | bad / unknown / unverifiable signature — *the fail-closed catch-all* |

   Each kitchen *reaches* the same six strings from a **native, non-stringly** primitive — **no `parse .message` in either**: TS reads **jose v6's `err instanceof errors.*` + `err.claim`** (`JWTClaimValidationFailed.claim ∈ { exp, aud, iss }`); PY reads **`pyjwt`'s `isinstance`** (`ExpiredSignatureError`, `InvalidAudienceError`, `InvalidIssuerError`, and `DecodeError` *minus* `InvalidSignatureError` → Malformed). Everything unclassified — a real *signature* failure, a network fetch error, an unknown kid after re-fetch — **falls through to `Signature verification failed`**, the deliberately *opaque* catch-all: never a different string, never a 500, never a silent pass.

3. **The lighthouse stays on the street.** A new **`PUBLIC_PATHS`** set — `{ "/", "/docs", "/redoc", "/openapi.json", "/health" }` in *both* kitchens — the door *returns early* (call next) for anything on it. The **lighthouse `/health`** (ADR-010's no-cellar liveness probe) and the *menu* docs are *public by design*; a load balancer and an `OpenAPI` consumer must not need a badge. Every *data* route (workspaces / projects / issues, and the Day 10-11 ownership model) is *behind* the door. **The /health lighthouse parity crack** — the TS set shipped *without* `/health` while the PY side had it (PY `/health` = street, TS `/health` = locked data route) — is **fixed** by adding `/health` to the TS set (**+2 lighthouse tests**), so the set *mirrors* the PY side exactly (the TS lighthouse *test* list stubs `/redoc` too, because Fastify ships no `/redoc` route where FastAPI does — the *set* stays a 1:1 mirror; only the stub list differs, and that difference is commented in the test). ADR-010's no-cellar lighthouse keeps working *through* the front-of-house wall.

4. **Doorless reader (the ADR-008 shape, re-applied to the door).** **`if (!process.env.AUTH0_DOMAIN) return`** in the door hook / middleware: with **no tenant configured, the reader is absent entirely** — the house runs as the pre-Day-8 street (the Day 3 stub behavior: every route open). This is *why* the whole suite and the **ADR-010 zero-service CI gate stay green with `AUTH0_DOMAIN` unset** — *no* env is *doorless*, which *is* the no-env the gate already runs under. A *configured* door (tenant set) engages the reader on all non-public paths. **But the boundary is coarser than a single env:** setting `AUTH0_DOMAIN` *alone* still engages the reader against the **default audience** `"foundry-taskflow-api-aud"` (the `??` fallback). The reader is *only* fully off when `AUTH0_DOMAIN` is *unset*. So "doorless" in this ADR means *no tenant configured* — **not** "any env missing." That asymmetry is the **ADR-008 `no env` claim's real shape**: we *keep a* `AUTH0_AUDIENCE` base (a sane default the reader falls back to), so doorless is keyed to `AUTH0_DOMAIN` specifically, and the deploy's *doorless* is "no `AUTH0_DOMAIN`," not "no `AUTH0_*`."

5. **Trust boundary on the *tenant* (the multi-tenancy seam).** The **`AUTH0_DOMAIN`** from *env* is *trusted operator config* — used as-is. A per-request **`X-Tenant-Domain`** header may *override* the tenant, but it is **untrusted client input**: it is gated on an **`ALLOWED_DOMAINS`** allowlist (the one registered Auth0 tenant today) and a stranger domain **fails closed** to `Signature verification failed`. Without the header there is *no* allowlist check — a single-tenant allowlist must not block the *configured* tenant itself (an override of the *same* tenant that the env already names is the no-op case; only a *different* header tenant is gated). This is the *seam from which Day 10-11's ownership/RBAC work descends*: the door already reads a *tenant*, so "who's asking at *which* tenant" is one layer up from today's door — recorded, not built (ADR-008's *cellar* is still single-tenant).

6. **The counter is bolted behind *one* reader, in *both* tracks.** The **TS counter** (Fastify, `:8000`) registers `doorHook`; the **PY counter** (FastAPI, `:8001`) registers `AuthenticateBadgeMiddleware`. The **JWKS** comes over **`https://{domain}/.well-known/jwks.json`** (the PY side notes Auth0 returns **426** over plain HTTP — https is mandatory). The reader hits the *network* only in the *live* path; under tests it is *stubbed* (the PY tests seed the JWKS cache with a **locally-generated** RSA keypair and monkeypatch `_fetch_jwks`; the TS tests drive `app.inject` with a locally-issued token, **no external network**). This is what keeps the door *inside* ADR-010's zero-service gate (see *Consequences*).

## Consequences

**Positive**
- **The house gets its first door — and the street doesn't notice.** `/health` (ADR-010's no-cellar liveness) and the `/` street and the menu **stay open** through the front-of-house wall: ADR-010's gate is *invariant* (the lighthouse reads a lighthouse, which is on the *street*). The counter now answers *who you are* to data rooms while still serving the street.
- **The parity wall has a second, *meaningful* gate.** The **6-string 401 contract** is asserted in both kitchens from *native* primitives (jose `instanceof` / PyJWT `instanceof`) — the day's real parity work. The counter cannot 401 *differently* by kitchen: same six `message` strings, same envelope.
- **One reader, many rooms — the Day 10-11 scale-up is *additive*.** `request.user` is typed as the badge **payload** in each framework (`JWTPayload` on the Fastify request module; `request.state.user` in the PY middleware). **No data route changes shape** to become authenticated; the *global* door already ran first. Day 10-11 (ownership/RBAC) reads `request.user.sub` *up one layer* — the reader is already on the bus (ADR-007's *receptionist-as-middleware* shape, generalized to the *front of the house*).
- **Fail-closed with no discretion to drift.** Unknown kid → **one re-fetch** → still unknown → `Signature verification failed` (not a 500, not an open door). Network-down → same. Bad signature → same. The *only* way the reader is *right* is a valid badge; every other path is the *same* opaque string. There is **no** codepath that lets an unauthenticated caller through a *configured* door.
- **The stub is demoted, not deleted.** The Day 3 `{ sub: "dev" }` reader survives *only* as the no-env doorless path — the local-dev / no-config story. On a configured door the reader is the real JWKS verifier. No dead code on the live path.

**Negative**
- **The TS / PY readers are *isomorph, not identical code* — by design, with one *real* asymmetry to police.** Same inputs, same 6 strings, same envelope. But the crypto *stacks* differ: TS **jose v6** (`createRemoteJWKSet` + `instanceof errors.*` + `err.claim`) vs PY **PyJWT + a hand-rolled JWKS fetch** (`isinstance`). The *failure-mapping* functions (`mapFailReason` / `map_fail_reason`) are the seams where a *new* failure type in *one* library can silently diverge the *other* kitchen's string. (jose v6's `jwtVerify` *returns the payload*; v5 *threw* it — the day rode a **v5→v6 behavior change** and had to re-derive the `mapFailReason` mapping; **pinning jose v6.2.12** is load-bearing, and the mapping is *not* a "safe refactor".)
- **The lighthouse set is a *third* parity surface that must be kept in lockstep.** `/health` on the street *and* the menu on the street is now a *tested* invariant in both kitchens; a future route added *without* checking "is this public?" and a future *edit* to one kitchen's set that the other doesn't mirror will 401 something that should be open (or *open* something that should be locked). The PY test already stubs the full menu; the TS lighthouse test list differs only by the `/redoc` stub (Fastify ships no `/redoc`) — a *commented*, deliberate divergence, kept *inside* the identical *set*.
- **The JWKS network read lives *inside* the "zero-service" CI gate.** Both kitchens' *readers* call the remote JWKS; under ADR-010's gate it is *stubbed* (no real network, no real Auth0). So the door's *happy path with a real remote JWKS* is **not** exercised in CI — only doorless + stub + the 6-failure strings are. The live-JWKS path is a **known debt**, deferred (it is ADR-010's "the gate tests the counter, never the cellar" applied to the door: no *live auth provider* in a zero-service gate).
- **A *new* dependency on each track's toolchain** (`jose` ^6.2.12 in TS; `pyjwt[cryptography]` ^2.14 + `httpx` ^0.28.1 in PY), each pinned and each a *supply-chain + build-script* surface the Day 7 pnpm wall (ADR-010) *just* taught us to police — a door that drags a new *install* risk onto the zero-service gate.
- **Doorless-ness is now *coarser* than "no env."** With `AUTH0_DOMAIN` set but `AUTH0_AUDIENCE` missing, the reader is *on* with the default audience — so "doorless" is keyed to *one* specific env var, not to "no env at all." The ADR-008 `no env` mental model does *not* transfer 1:1 to the door: **doorless = "no `AUTH0_DOMAIN`," specifically.** Recorded so a future deploy "cleans up" the `AUTH0_AUDIENCE` base and silently changes the doorless boundary.

**Mitigation**
- **The parity wall *tests the strings, from native primitives.* Both kitchens' **verifier tests** assert the *exact* six `message` strings and the ADR-007 envelope over `app.inject` / TestClient with **locally-issued** tokens (real RSA sign / verify against a locally-minted JWKS) — no live network. A new failure type in *either* library that maps to a *wrong* string (or to 500, or to a *silent pass*) is **red on push** in *both* kitchens, because the *contract* strings are asserted on both sides. The *six strings* — not the *implementation* — is the parity assertion.
- **The six-string *contract* is the seam, not the implementation.** Each kitchen's `mapFailReason` is a small, *exhaustive-ish* function with `Signature verification failed` as the *explicit* `else` (the fail-closed catch-all). The *comment where the door used to be* (ADR-008's pattern) names *why* each branch is a native `instanceof` and *why* the catch-all is one string — the day's known debt (a *new* jose/PyJWT release adding a failure type) is met at *one* small function, not scattered across routes.
- **The lighthouse/menu set is *one* source per kitchen + a *commented* mirror.** The PY test asserts the *full* public list including `/health`; the TS *set* is byte-mirrored to it (the TS *test stub list* adds a `/redoc` stub, commented, because Fastify has no `/redoc` route). The **parity crack found on Day 8** (TS set missing `/health`, PY had it) is the *reason* the set is tested in *both* kitchens, not one — the fix lands with +2 TS lighthouse tests so a *mirror* drift is red on push.
- **The "no env is doorless" load-bearing fact is asserted in *both* tests.** Each kitchen's reader suite has a `AUTH0_DOMAIN` **unset/empty** test that asserts the door is *absent* (a no-token request reaches the *street/lighthouse*; the stub's `request.user = { sub: "dev" }` path is the no-config world) and, symmetrically, a *configured-t* stranger-tenant test that asserts **fail-closed**. This pins *both* halves of the ADR-008-shaped decision: doorless *and* fail-closed.
- **The door stays *inside* ADR-010's gate because *both* kitchens stub the JWKS** — the *live* JWKS fetch (a real `https` to Auth0) is the *one* path not in CI. The known debt is *named* (below) and *bounded*: it is Phase 2's "make it right" (coverage bar, live-provider smoke) to exercise, not a Day 8-9 gap. The gate is *not* made flaky to cover it (ADR-010: no `services:` / no live provider in a zero-service gate).

**Deprecation/Upgrade**
- **The door is a *twin* to ADR-008's doorless *deploy*, and the two must change *together* or the "no env" story lies.** The *deploy* (ADR-008) and the *reader* (this ADR) both use "no `AUTH0_DOMAIN`" as the doorless key. A future deploy that *always* injects `AUTH0_DOMAIN` (real tenants in every env) makes the *reader* permanently on and the *doorless path* untestable *in deploy* — at that point the *doorless* test (no `AUTH0_DOMAIN`) must move to a *local / test-only* env, or the ADR-008 `no env` claim re-scopes. The two ADRs share one env var's meaning; neither edits the other's assumption silently.
- **The hand-rolled PY JWKS reader is *the* upgrade candidate — and the *known debt*.** The ~40-line fetch-cache-keyrefetch reader works and is *tested* (seeded JWKS + one re-fetch on unknown kid). The upgrade path — a *library* JWKS provider on *one* track (e.g. a typed `jwks-rsa`/`py-jose`-style reader), or *harmonization* where both tracks use the *same* primitive family — is **Phase 2 / Sprint 5** work, *not* a Day 8-9 gap. On the thin house, a *tested, cached, fail-closed* 40-liner is the *correct* size; the debt is *parity risk* across two crypto stacks, and *that* is what the six-string contract *tests* (Consequences + Mitigation) even while the *implementation* stays hand-rolled. **It is the day's one *named* debt** — the *next* day that touches a badge should *prefer* to harmonize the two readers on one library family, or at least keep the six-string contract asserted on *both.*
- **The reader becomes the *root domain* of the identity layer in v4 (`identity/` → Auth, Users, RBAC, ROOT).** Day 10-11 (v4: *Workspace ownership, basic RBAC* — Plane workspace-members; *Owner can invite, member can view*) will read **`request.user.sub`** to answer *who's asking*. The reader *stays* on the bus (ADR-007's middleware shape, generalized); the *authorizer* (RBAC: owner/member/invite) is a *new* layer *above* it — this ADR deliberately *does not* build authorization, only *authentication*. The seam is one read: `request.user.sub` is already there; "is this user an *owner* of *this* workspace" is Day 10-11.
